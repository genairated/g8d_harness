# SPEC — UI 設計器（元件庫 + 版面設計 + 可點擊原型）

> Status: **定版 v1.1**（決策表 §2 全數拍板 — Charles 2026-08-19「全部按照你的建議」＋追加 D12、D13）｜Owner: Charles + Hana｜規劃日 2026-08-19
> 一句話：在 Harness 裡做一套**離線、本地優先的 UI 設計能力**——先建「元件庫」（Storybook 的概念），再用元件在「畫布」上拼出各裝置（桌機 / 平板 / PDA 手持）的畫面（Figma 的概念），再匯出成**可點擊操作的原型**；設計過的畫面可**沉澱成範本**供下次挑選；並用一套**設計指南**讓 Hana 在建 UI 時「先問對問題、再選對元件」。另提供技能：丟一張擷圖或範例網頁給 Hana，她自動拆出元件、建庫、並把畫面畫出來。
> 影響範圍（預估）：`portal/views/uidesign.js`（新 view）、`portal/index.html`（面板容器）、`portal/server.js`（`/api/ui/*` 路由）、`portal/views/settings.js` 的 `NAV_ITEMS` 與 `DEFAULT_NAV`（納入既有功能選單開關）、`<workspace>/.harness/uidesign/`（持久化，天條：只寫當前工作區）、`global-knowledge/commands/ui-from-image.md`（新技能）。

---

## 1. 動機與定位（與既有能力的分界）

- 這**不是**白板（`SPEC-whiteboard`：手繪風自由思考畫布，Excalidraw，輸出 PNG）。UI 設計器要的是**像素級對齊、裝置尺寸、真實元件外觀**，手繪風不適用。
- 這**不是**簡報（`SPEC-presentation-core`）也**不是**文件流程圖（`SPEC-doc-editing` 的 BPMN）。
- 定位：**平台級全域功能**（比照白板，進側欄 + 納入 `harness.json` 的 `nav` 顯示開關，不另建機制）。

| D11 | **設計指南的作用力道**：只給建議 / 會擋下不合規的設計 | **第一版只給建議與提問，不強制擋**。理由：設計初期硬擋會很煩。之後可加一個「檢查」按鈕做事後稽核（列出違反條款的地方）。 | ✅ 同意（2026-08-19）|
| D7 | **擷圖轉元件的準確度期望** | 明講：這是**啟發式**，Hana 會盡量還原版面與元件切分，但**顏色/間距/字型不會 100% 一致**，定位是「省掉 80% 白工的草稿」，不是像素級複刻。若期望是像素級複刻，這個功能要重新設計（改走「切圖 + 標註」路線）。 | ✅ 同意（2026-08-19）|
| D12 | **設計系統的作用範圍：全平台共用一份，還是每個工作區各自一份** | **每個工作區各自一份，沒有 global 版本**（Charles 2026-08-19 追加指示）。理由：Hana 同時管多個專案，各專案對應不同系統，會有各自的元件庫、各自的設計指南、各自的畫面與範本，混在一起會互相污染。實作＝所有設計系統資料一律落在 `<workspace>/.harness/uidesign/`，**不做全域回退**（找不到就是空的、請新建，絕不去讀別的工作區或平台預設）。唯一例外是「內建骨架範本」與「決策表出廠預設」，它們是**種子**：新工作區第一次使用時複製一份進該工作區，之後就是該工作區自己的，改了不影響別人。 | ✅ 拍板（2026-08-19）|
| D13 | **要不要支援「用螢幕尺寸（吋）設計」而非只有解析度** | **要，且採業界標準的密度無關單位（Android dp / iOS pt，1dp = 1px@160dpi），不自創新單位**。新建畫面可選「解析度模式」或「尺寸模式（吋＋實體解析度 → 算密度倍率）」；資料格式加 `unit`／`scale`，舊畫面視為 px/1x 向後相容。理由：這正是指揮官描述的痛點（高 PPI 元件變小、低 PPI 變大）在業界的既有解法，硬體與作業系統本來就照這套走，跟著標準做才能與真實裝置對得上。 | ✅ 拍板（2026-08-19 追加）|

## 3. 架構分層

| 層 | 內容 |
|---|---|
| **L1 元件庫**（Storybook 概念） | 每個元件 = 名稱 + 分類 + HTML 模板 + CSS + 參數（variant/args）+ 預覽。可看所有變體、可即時改參數看效果。 |
| **L2 設計畫布**（Figma 概念） | 一個 Screen（畫面）= 一個裝置尺寸的畫框 + 一堆元件實例（位置、尺寸、參數覆寫）。支援吸附對齊、多選、圖層、複製畫面。 |
| **L3 原型**（可點擊） | 在元件實例上掛「點擊 → 前往某畫面」；預覽模式下用真實裝置外框播放，可操作。 |
| **L4 技能**（AI 建庫） | 給圖／給網址 → Hana 判讀 → 產出元件庫 + 畫面草稿，直接落進 L1/L2 的資料。 |
| **L5 範本庫** | 設計好的畫面可「另存為範本」；下次新建畫面時從範本挑選，套用後只需替換內容。範本存結構與元件引用，不存死資料。 |
| **L6 設計指南** | 一套人可讀可改的規範（版面、間距、色彩、字級、元件選用準則）。其中**元件選用準則**是可被 Hana 執行的決策表——她建 UI 前會依表向你提問，答完才決定用哪種元件。 |

## 4. 裝置預設（D 系列拍板後可微調）

| 類型 | 預設尺寸 | 備註 |
|---|---|---|
| 桌機 Web | 1920×1080（FHD）、1440×900、1280×800 | 可自訂 |
| 平板 | 1024×768（橫）、768×1024（直） | |
| 手機 / PDA 手持機 | 390×844（一般手機）、480×800 與 720×1280（工業 PDA 常見比例） | PDA 情境需支援**實體按鍵區**與**大按鈕/戴手套可點**的元件範本 |

**自訂尺寸（UID-09b）**：畫布左側裝置選單提供「＋ 自訂尺寸…」，輸入寬高（可命名）後建立畫面，
該尺寸同時存進 `<workspace>/.harness/uidesign/devices.json`，之後就跟出廠預設一樣列在選單中可重複選用，
也可從選單下方移除（移除只影響選單，已建立的畫面 frame 不變）。D12 工作區隔離：自訂尺寸只屬當前工作區。
API：`GET/POST /api/ui/devices`、`DELETE /api/ui/devices/:id`。寬高相同時不重複新增；若等於某出廠預設則直接沿用該預設。

## 5. 資料存放（天條：只寫當前工作區）

```
<workspace>/.harness/uidesign/
  library.json        # 元件庫：元件清單、參數定義、CSS token
  components/<id>.html / <id>.css
  screens/<id>.json   # 每個畫面：裝置、畫框尺寸、元件實例、跳轉連結
  index.json          # 專案/清單索引
```
- 所有讀寫 API 走 `resolveWorkspace(req)` + `path.resolve()` 正規化（比照排程工作區隔離鐵則）。

### 5.1 工作區隔離（D12 鐵則，設計與實作皆須遵守）

1. **每個工作區一套完整、獨立的設計系統**：元件庫、畫面、原型、範本、設計指南（含決策表），全部只存在 `<workspace>/.harness/uidesign/`。
2. **不做全域回退**：某工作區沒有元件庫，就顯示「這個專案還沒有元件庫，要新建或從別的專案匯入嗎」，**絕不**自動去讀 `global-knowledge/` 或其他工作區的資料。
3. **種子（seed）而非共用**：內建骨架範本、設計指南出廠預設條款，在該工作區第一次啟用本功能時**複製**一份進去；此後該工作區怎麼改都不會影響其他工作區，平台升級也不覆寫已存在的檔案。
4. **技能同樣受隔離**：`/ui-from-image`、`/ui-design` 讀寫的一律是**當下工作區**的元件庫與指南（天條）；提問時依的是該工作區的決策表。
5. **跨工作區只能「明示匯入」**：提供「從其他工作區匯入元件庫／指南／範本」的動作（複製一份過來，複製後兩邊各自獨立、不連動）。此功能排在 UID7，非第一版必要。
6. **驗收條件**：切換工作區後，元件庫／畫面／範本／指南清單必須整組換掉；任一面不得出現他工作區的項目（比照排程工作區隔離的驗收方式）。

## 6.1 設計指南（L6）

存放：`<workspace>/.harness/uidesign/guideline/`
- `guideline.md`——人可讀的規範全文（版面網格、間距刻度、色彩語意、字級階梯、無障礙、PDA 特例如大按鈕/戴手套/實體按鍵）。你可以直接編輯。
- `decisions.json`——**機器可讀的元件選用決策表**，Hana 建 UI 時照這張表提問。

決策表的一條規則長這樣（示意，非程式碼細節）：

| 情境 | Hana 會問你的問題 | 依答案的選用結果 |
|---|---|---|
| 要讓使用者從一組固定選項中選 **一個** | 選項有幾個？需要同時看到全部嗎？畫面寬鬆還是擁擠？ | 2–3 個且需一眼看完 → Radio 清單；4–7 個 → Segmented / Radio；8 個以上或畫面擁擠 → 下拉選單；上百筆 → 可搜尋的下拉 |
| 要選 **多個** | 選項數量？是否需要全選？ | 少量 → Checkbox 清單；大量 → 多選下拉 + 已選標籤；需比較欄位 → Grid 勾選 |
| 呈現 **一批資料** | 每筆要看幾個欄位？要排序/篩選/批次操作嗎？行動裝置也要看嗎？ | 多欄位＋要排序 → 資料表格；少欄位＋重瀏覽 → 卡片清單；手機/PDA → 清單列 + 明細頁 |
| **狀態**類欄位 | 狀態值固定嗎？幾種？使用者常改嗎？ | 固定 2–3 種且常改 → Radio/切換；固定多種 → 下拉；唯讀 → 狀態標籤（Badge） |
| **是/否/忽略** 這類三態 | 是否有預設值？誤觸代價高嗎？ | 三態且需明示 → Radio 清單（你舉的例子）；純開關 → Switch |
| 日期、數量、金額等輸入 | 範圍限制？需不需要快速選（今天/本月）？ | 依表決定日期選擇器 / 區間 / 純輸入 |

規則可由你增修；Hana 每次依表提問，答完把選用理由記在畫面的備註裡，日後可追。

## 6.2 範本（L5）

存放：`<workspace>/.harness/uidesign/templates/<id>.json`（＋一張縮圖）。
- 來源一：把已設計好的畫面「另存為範本」，Hana 會自動把死內容抽成佔位（標題、欄位名、清單筆數）。
- 來源二：Hana 依設計指南預先產出的常用骨架（登入頁、清單+搜尋、主檔明細、儀表板、PDA 掃碼作業頁）。
- 使用：新建畫面 → 挑範本 → 套用 → 只改內容。挑選時可依裝置類型與情境篩選。

## 7. 分階段（細粒度任務待決策拍板後寫進 `.worktable/TASK.md`）

- **UID1 元件庫（L1）**：資料格式 + CRUD API + 元件庫面板（清單／編輯／變體預覽）。可獨立驗收：能手建一顆按鈕、切三種變體、預覽正確。
- **UID2 設計畫布（L2）**：裝置畫框、拖放元件、吸附對齊、圖層、存檔續編。可獨立驗收：拼出一個登入頁並重新載入後完整還原。
- **UID8 畫布編輯操作性（L2 補完，Charles 2026-08-19 追加）**：**復原／重做**（狀態堆疊約 50 步，工具列按鈕＋`Ctrl+Z`／`Ctrl+Shift+Z`，連續拖曳合併為一步）、**平移**（空白鍵拖曳／中鍵拖曳／滾輪捲動；與「空白處拖曳＝框選」明確分流）、**縮放**（`Ctrl`＋滾輪以游標為中心，工具列 `+ / − / 100% / 符合視窗`；「符合視窗」＝把整個畫框等比縮到剛好塞滿可編輯區，是常用預設，見 §7.1）、**全螢幕編輯**與**全螢幕預覽（唯讀）**（見 §7.1）。**一律比照 `portal/views/whiteboard.js`／`portal/views/pm.js` 既有互動與全螢幕慣例，不自創新做法**（既有標準優先原則）。可獨立驗收：誤刪元件能救回、縮到 50% 仍能精準拖放吸附、大畫框在小視窗中可平移看完、F11 級的全螢幕下工具列與主題切換仍可用。
- **UID3 原型（L3）**：跳轉連結 + 預覽播放模式（+ 依 D6 決定是否做離線匯出）。
- **UID4 技能 `/ui-from-image`（L4）**：擷圖／網址 → 元件庫 + 畫面草稿。依賴 UID1、UID2 的資料格式定案。
- **UID5 範本庫（L5）**：畫面另存為範本、範本挑選與套用、內建骨架範本。依賴 UID2。可獨立驗收：把一個做好的清單頁存成範本，新建畫面套用後結構完整、內容已抽成佔位。
- **UID6 設計指南（L6）**：`guideline.md` + 元件選用決策表 + 技能 `/ui-design`（依表提問 → 產畫面）。可獨立驗收：指揮官說「做一個工單狀態編輯頁」，Hana 會先問狀態有幾種、是否常改，再依答案選對元件並說明理由。
- **UID10 語意標記（來源標記）**：畫面 `purpose`／`origin`／`sourceTemplateId`、元件實例 `role`／`slot`，＋屬性面板補標 UI 與覆蓋率檢視。是「日後自動重套」的前提，見 §7.3。
- **UID11 依範本重套**：對已標記畫面套上新範本（逐張確認／整批套用），保留內容、產生可退回的新版本、列出未能自動重套的項目。見 §7.3。
- **UID12 UI操作演示（清單＋重播＋簡報模式）**：與畫面、元件並列的第四種資料；一條流程＝有順序的步驟，每步一張畫面＋一句操作說明。見 §7.4。可獨立驗收：建一條「新進人員報到」流程、走完五步、進簡報模式全螢幕講一遍。
- **UID13 UI操作演示離線匯出**：把一條流程打包成客戶可自行開啟的離線資料夾。見 §7.4.4。可獨立驗收：匯出後把資料夾複製到別處、斷開本系統仍能完整播放。
- **UID7（後續）**：離線 zip 匯出、流程包範本、設計指南事後稽核（列出違反條款處）、**跨工作區匯入**（把某工作區的元件庫／指南／範本複製一份到當前工作區，複製後各自獨立，見 §5.1-5）。

> 建議實作順序：UID1 → UID2 → UID6（先有指南，後面 AI 產出的東西才有品味一致性）→ UID3 → UID5 → UID4。UID4 放最後，因為它最吃前面所有資料格式定案。

### 7.1 全螢幕與縮放（Charles 2026-08-19 追加，併入 UID8）

| 項目 | 定義 | 實作慣例 |
|---|---|---|
| **全螢幕編輯** | 把畫布區（含工具列、元件面板、圖層面板）整塊送進全螢幕，仍可完整編輯。 | 比照 `whiteboard.js` 的 `toggleFullscreen()`：Fullscreen API 只渲染該元素子樹，故**主題切換鈕必須複製一份到畫布工具列**，否則全螢幕下按不到。退出時要還原圖示與事件解除（白板已有 `fullscreenchange` 監聽與 unmount 清理，照抄）。 |
| **全螢幕預覽（唯讀）** | 只渲染畫框與元件、**隱藏所有編輯介面**（拖曳把手、吸附線、格線、選取框、圖層面板），滑鼠不可拖動元件，`Esc` 或按鈕退出。 | 與 UID3 的「原型播放」**分工明確**：UID8 的預覽是**靜態看版**（純檢視實際外觀，不含跳轉互動）；UID3 才加上「點擊 → 前往某畫面」的可操作原型。兩者共用同一個唯讀渲染函式，UID3 只是在其上掛跳轉。 |
| **工具模式（Charles 2026-08-19 追加）** | 工具列常駐兩顆工具鈕（箭頭＝選取／編輯元件、手掌＝拖曳整個畫布），比照白板；快捷鍵 `V`／`H`，按住空白鍵仍可在箭頭模式下臨時平移。 | 手掌模式下畫布游標為 `grab`，左鍵拖曳即平移，元件拖曳與框選一律停用（`isPanMode()` 統一判斷，中鍵平移不受模式影響）。 |
| **全螢幕的比例與還原（Charles 2026-08-19 追加）** | 進入全螢幕自動套用一次「符合視窗」，離開時還原進入前的縮放與捲動位置。 | 全螢幕改變可視區大小，必須等兩個 animation frame 版面重排完再量測；唯讀預覽同理，`requestFullscreen()` 後用實際容器尺寸重算比例並監聽 `resize`。**畫布與預覽的置中一律用 `margin:auto`，不可用 flex `justify-center`**——內容大於容器時 flex 置中會把左上角推出可視區且捲不回來（1920×1080 畫框左上被切掉即此因）。 |
| **縮放** | `Ctrl`＋滾輪以游標為中心；工具列 `＋ / － / 100% / 符合視窗`；級距比照白板。 | **「符合視窗」是重點需求**：1920×1080 這種畫框在一般螢幕上放不下，需能等比縮到剛好塞進可編輯區。縮放只改視覺呈現，**畫面資料永遠以畫框原生座標儲存**（元件座標不因縮放而改寫），所有滑鼠座標一律 `/ state.zoom` 還原成畫框座標後再吸附／落點。切換畫面或改變畫框尺寸時預設套用一次「符合視窗」。 |

### 7.1.1 資料重新整理（Charles 2026-08-20 追加）

畫面／元件可能由**技能（如 `/ui-from-image`）或另一個分頁**在背景直接寫進工作區檔案，前端沒有推播機制，因此必須提供手動重抓：

| 項目 | 定義 |
|---|---|
| **重新整理鈕** | 畫布分頁左欄「畫面」標題列右側的 `refresh-cw` 圖示鈕。按下後一次重抓：畫面清單、元件庫（清空 `compCache` 重建）、裝置與機型清單，並重載目前開啟的那張畫面；重抓前先 flush debounce 中的存檔，避免伺服器版本蓋掉尚未存檔的編輯。目前畫面若已被刪除，退回「未開啟畫面」狀態。 |
| **切分頁自動重抓** | `switchMode('canvas')` 每次都呼叫 `loadScreens()`（不再只在首次載入時抓），切回畫布分頁即看到新畫面。 |

## 7.2 以「螢幕尺寸」設計（UID9，Charles 2026-08-19 追加）

**問題**：傳統用「解析度」設計 UI，同一份設計丟到高 PPI 螢幕上元件會變得很小、丟到低 PPI 螢幕上會變得很大——尤其手機解析度百百種，但使用者實際感受到的是「這台是 6 吋機」。

**做法（D13，採業界標準、不自創）**：導入**密度無關單位**——即 Android 的 `dp`（1dp = 1px @160dpi）與 iOS 的 `pt`（@1x）。這是行動與桌面 UI 業界二十年來的共同解法，本系統直接沿用，不發明新單位。

- 新建畫面時提供**兩種模式**：
  1. **解析度模式**（現況，`px`）：直接給實體像素，適合固定螢幕的桌機／看板／工業 PDA。
  2. **尺寸模式**（新增，`dp`）：給**螢幕對角吋數 + 實體解析度**（或直接挑機型），系統算出 PPI 與**密度倍率** `scale = PPI / 160`，畫框以 `dp` 為單位（＝實體像素 ÷ scale）。同樣是 6 吋手機，不論 1080×2400 還是 1440×3200，畫框都是同一個 dp 尺寸，設計一次即可。
- **畫面資料格式擴充**：`screens/<id>.json` 增加 `unit`（`px` | `dp`）、`diagonalInch`、`nativeWidth/nativeHeight`（實體像素）、`scale`（密度倍率）。既有畫面沒有這些欄位時一律視為 `unit: "px"`、`scale: 1`（**向後相容，不得破壞 UID2 已存的畫面**）。
- **呈現**：預覽／原型可切「以 dp 呈現（設計視角）」或「以實際解析度呈現（裝置視角，整體乘上 scale）」，讓指揮官親眼看到同一份設計在 1x／2x／3x 螢幕上的實際大小。
- **機型預設表**：內建常見對照（如 6.1 吋 / 1179×2556 / ~460ppi / 3x、6.7 吋 / 1290×2796 / 3x、13 吋筆電 / 1920×1080 / 1x、13 吋 Retina / 2560×1600 / 2x、工業 PDA 4 吋 / 480×800 / 1x），可自行增修；此表比照 D12 當**種子**複製進工作區，不做全域共用。
- **與設計指南（UID6）的銜接**：間距刻度與字級階梯一律以 dp 表述（8dp 網格），指南文字同步改寫。


## 7.3 畫面優先、標記隨行、之後重套（Charles 2026-08-20 拍板）

**背景**：元件庫／範本／設計指南雖已就緒，但指揮官手上已經有想做的畫面，先為了建庫而想像一堆用不到的元件並不務實。因此工作順序改為：**先畫想得到的畫面 → 之後再補情境流程與範本 → 最後回頭把既有畫面重新套上新範本**。

**唯一前提**：畫面裡必須看得出「結構」，否則對系統而言只是一張圖，之後只能人工一頁一頁重畫。所以建畫面時**同步留下語意標記**（下稱來源標記），這是「之後能不能自動重套」的分水嶺。

### 7.3.1 語意標記（UID10）

| 層級 | 欄位 | 說明 |
|---|---|---|
| 畫面 | `purpose` | 這張畫面在做什麼：`login`／`list`／`detail`／`form`／`dashboard`／`scan`／`other`。 |
| 畫面 | `origin` | 這張畫面怎麼來的：`manual`（手拉）／`template`（套範本）／`image`（`/ui-from-image`）／`skill`（`/ui-design`）。 |
| 畫面 | `sourceTemplateId` | 若來自範本，記下範本 id 與套用時的範本版本，供日後比對。 |
| 元件實例 | `role` | 這一塊在畫面裡的角色：`header`／`nav`／`field-group`／`field`／`action-bar`／`action`／`list`／`list-item`／`card`／`text`／`media`。 |
| 元件實例 | `slot` | 對應範本插槽名（如 `title`／`primary-action`／`search`），有 slot 才能被自動重套精準對位。 |

- **不新增額外提問負擔**：`/ui-design` 的決策表流程本來就在問「這是什麼欄位、幾個選項、常不常改」，答案直接寫成標記；`/ui-from-image` 判讀時本來就在分類區塊，一併寫入。手拉畫面則在屬性面板提供下拉選單補標。
- **向後相容**：既有畫面沒有這些欄位不受影響，一律視為未標記。
- **覆蓋率檢視**：畫布提供「標記檢視」，標出未標記的元件，讓指揮官知道哪些畫面之後無法自動重套。

### 7.3.2 依範本重套（UID11）

- 對象：已有標記的畫面。選一個範本 → 依 `slot`／`role` 對位，把元件換成新範本指定的元件與樣式，**保留原本的文字內容與資料**。
- 兩種模式：**逐張確認**（預設，改一張看一張）與**整批套用**（確認方向正確後再用）。
- **可逆**：重套一律產生新版本，原畫面保留於 `screens/revisions/`，可一鍵退回。
- **誠實回報**：無法對位的元件一律原樣保留，並在結果列出「未能自動重套」清單與原因（未標記／找不到對應 slot／範本無此角色），不得靜默丟棄或亂猜。

**風險與時間（如實記錄）**：重套是產生新版本、可退回，風險低。真正的風險是**前期畫了大量畫面卻沒留標記**——那筆人工重畫成本隨畫面數線性增加，因此 UID10 應盡早做、不要等畫了幾十張才補。UID11 可等範本真的補齊再做，不急。

**實作備忘（2026-08-20，UID11 完工後補）**：

- **slot 詞彙需要範本端也標記，不是只有畫面端**：UID10 只讓「畫面元件」可以標 `role`/`slot`，但對位引擎要拿「範本元件」的 `role`/`slot` 當比對目標——5 個內建骨架範本（`portal/uidesign.js` 的 `seedTemplateDefs`）原本完全沒有這兩個欄位，已補上。詞彙盡量沿用 §7.3.1 建議的可讀名稱：`title`／`primary-action`／`search`／`field-account`／`field-password` 當 slot；`role` 沿用 UID-37 既有的 `ROLE_OPTS`（`header`/`nav`/`field-group`/`field`/`action-bar`/`action`/`list`/`list-item`/`card`/`text`/`media`）。同一 `role` 若畫面/範本上有多筆（例如多列清單、多張卡片），靠**池化取用**（依原順序逐一消耗）處理，不需要各自取不同的 slot 名。
- **對位演算法**：`portal/uidesign.js` 的 `restyleMatchScreen(screen, template)`（純函式，無副作用）——依範本元素順序逐一找來源：先比對 `slot` 完全相同、找不到再退而求其次比對 `role`（皆從「尚未被消耗」的來源元件池挑）。對上了：新元素＝範本這格的 `componentId`/位置/大小/`variantIndex`（風格與結構全部換新），`overrides`＝範本這格自己的預設值為底，只有「範本這格的 overrides 鍵本來就有」的鍵才會被來源同名鍵覆蓋（保留內容、但不會把來源多出來的欄位硬塞進新元件不認得的地方）；`link`（跳轉設定）也視為畫面資料一併保留。對不上的：範本這格 → 用範本自己的預設內容產出（不無中生有套用來源資料）；來源這個元件 → 原樣保留、疊在新結構之後（絕不丟棄），並依序判斷回報原因：有 `slot` 但範本沒有此 slot → `slot-not-in-template`；有 `role` 但範本沒有此 role → `role-not-in-template`；兩者都沒有 → `unmarked`。
- **API**：`POST /api/ui/screens/:id/restyle/preview`（dry-run，不落地，供逐張確認模式先看結果）、`POST /api/ui/screens/:id/restyle/apply`（單張落地）、`POST /api/ui/screens/restyle/batch`（`{screenIds:[],templateId}`，整批套用，逐張獨立存快照、單張失敗不擋其他張）。
- **版本快照存放**：`<workspace>/.harness/uidesign/screens/revisions/<screenId>/<revId>.json`（+ 同層 `index.json`，新的在前）；`apply`/`batch` 落地前一律先存一份「重套前」快照。`GET /api/ui/screens/:id/revisions`／`POST /api/ui/screens/:id/revisions/:revId/restore`——**退回動作本身也會先把「即將被取代的當下版本」存一份**，所以退回可以再退回，不是單向門。
- **前端**：範本庫卡片新增「重套」鈕，開一個挑畫面＋選模式（逐張確認／整批套用）的疊層；逐張確認會依序呼叫 preview → 使用者按「套用這張」才真的呼叫 apply、按「略過這張」直接跳下一張；畫布工具列新增「版本記錄」鈕，列出該畫面的版本快照並可一鍵退回。


## 7.4 UI操作演示（Scenario Flows，Charles 2026-08-20 拍板；正式改稱見 §7.4.6）

**背景**：UID3 的可點擊原型只能「亂點跳轉」，沒有名字、沒有順序、沒有步驟說明、不能重播也不能交付給客戶。指揮官實際要的是一條**可以講給客戶聽的操作故事**：這個情境從哪一頁開始、每一步要做什麼、下一頁是什麼。這與 §6.2「流程包範本」是兩件事（那是骨架重用，這是操作敘事），規格原先把兩者混為一談，已於此節分家。

**定位**：UI操作演示是與「元件庫／畫面／範本」並列的第四種資料，是**畫面之上的一層敘事**，不改變畫面本身。

### 7.4.1 資料模型（UID12）

- 存放：`<workspace>/.harness/uidesign/flows/<id>.json` + `flows/index.json`（比照 screens 的 index 慣例，D12 工作區隔離鐵則照樣適用）。
- 流程欄位：`id`、`name`（如「新進人員報到」）、`description`（情境描述，可多行）、`device`（選填，供播放時決定畫框）、`steps[]`、`createdAt`／`updatedAt`。
- 步驟欄位：`screenId`（指向既有畫面）、`caption`（一句操作說明，如「在這裡輸入工號後按下一步」）、`hotspot`（選填，畫面上要點的位置 `{x,y,w,h}`，播放時以高亮框呈現）、`note`（選填，給客戶看不到的內部備註）。
- **失效不壞整條**：`screenId` 指向的畫面被刪除時，該步驟標為失效並在清單／播放時顯示提示，**整條流程仍可開啟與編輯**，不得因此讓流程無法載入。
- **刪畫面前先擋一次（Charles 2026-08-20 追加）**：刪除一張畫面時，若它已被任何流程引用，刪除確認對話框必須先列出「這張畫面被以下流程的第 N 步使用：〈流程名〉」，並要求二次確認（預設焦點在「取消」）；未被引用則維持原本的單次確認、不增加摩擦。此檢查在**伺服器端**判定引用關係（掃 `flows/index.json`）後回傳給前端呈現，不在前端自行推測。刪除仍可執行——這是提示，不是禁止；真的刪了則回落到上一條的失效處理。

### 7.4.2 建立與編輯（UID12）

- 第一版採**清單式建立**（Charles 拍板）：新增流程 → 逐步「加一步」→ 每步挑一張既有畫面（縮圖選單）＋填一句說明；步驟可拖曳排序、複製、刪除。
- 熱點（hotspot）為選填：在該步驟的畫面預覽上拉一個框即可，未拉則播放時不高亮。
- 「在原型上點一遍自動錄成步驟」列為後續（見 §7.4.5），第一版不做。

### 7.4.3 重播與簡報模式（UID12）

| 模式 | 行為 |
|---|---|
| **重播** | 在設計工具內一步一步走：上一步／下一步、直接跳到第 N 步、顯示 `3 / 8` 進度、側邊列出全部步驟可點選。畫面以唯讀渲染（沿用 UID8 的唯讀渲染函式，不自寫第二套）。 |
| **簡報模式** | 全螢幕、隱藏所有編輯介面，畫面置中等比縮放，步驟說明以字幕列呈現，鍵盤左右鍵／空白鍵換步。全螢幕實作**比照 `whiteboard.js` 的 `toggleFullscreen()` 慣例**（含主題鈕複製、`fullscreenchange` 監聽、unmount 清理），不自創。 |

- 兩種模式共用同一個播放核心，只差外框與是否進全螢幕。
- 與 UID3 的分工：UID3 是「自由點擊探索」，UID12 是「照順序走的敘事」。兩者可共存，播放時若步驟畫面上有 UID3 的跳轉連結，**以流程順序為準**，不因誤點而跳離流程。

### 7.4.4 離線匯出（UID13）

- 匯出一條流程成一個**自帶內容的資料夾**（含 `index.html` + 畫面 HTML／CSS + 素材），客戶用瀏覽器直接開，**不需要連線到本系統、不需要安裝任何東西**。
- 匯出內容＝簡報模式的播放器（上一步／下一步／進度／字幕）＋流程名稱與情境描述封面頁。
- 產物一律寫在**當前工作區**底下（`<workspace>/.harness/uidesign/exports/<flowId>/`），符合「產出留在所屬工作區」天條；壓縮成 zip 為選配。
- **誠實原則**：匯出前若有失效步驟或未能內嵌的素材，一律列出清單告知，不得靜默略過。

### 7.4.6 正式名稱：「UI操作演示」（Charles 2026-08-20 拍板，UID14）

**背景**：此功能原叫「情境流程」，但「情境流程」在客戶專案等工作區已是**文件家族的正式名稱**（`.documents/` 下有同名範本與文件），指揮官在對話中講「情境流程」時，Hana 只會聯想到那份文件，導致誤判。且此功能**沒有對應的全域技能**，模型無從得知它存在——誤判的根因是「缺一個全域 skill」，不只是撞名。

- 同時新增**全域技能 `/ui-demo`**（`global-knowledge/commands/ui-demo.md`），名稱與說明皆用「UI操作演示」一詞，讓任何工作區的對話都能正確命中此功能。

**改名範圍（只改「人看得到的字」，不動資料與 API）**：
- 前端分頁名、按鈕、標題、提示、匯出封面頁與匯出播放器的文案。
- `specs/SPEC-ui-designer.md`、`.worktable/TASK.md` 的敘述用詞。
- **明確不動**：`/api/ui/flows*` 路由、`.harness/uidesign/flows/` 目錄與 `<id>.json` 欄位名、`state.mode='flows'` 等程式識別碼——改這些會讓既有資料與既有匯出包壞掉，收益為零。

### 7.4.7 點擊熱區才前進（Charles 2026-08-20 拍板，UID15）

**需求**：客戶看演示時，不該只是被動按「下一步」；指揮官要的是「**點對按鈕才會前進**」——例如這一步的說明是「點選用料清單按鈕」，就必須真的點到畫面上那顆按鈕，演示才往下走。

- 步驟新增欄位 `advance`：`'next'`（預設，沿用現行「按下一步就前進」）｜`'hotspot'`（必須點擊熱區才前進）。**缺欄位＝`'next'`**，既有流程與既有匯出包行為完全不變（不回填、不遷移）。
- `advance:'hotspot'` 只有在該步驟**設定了 `hotspot`** 時才生效；編輯 UI 在沒有熱區時不得讓人勾選此選項（或勾選後即時提示要先拉框），不做「勾了卻卡死走不下去」的死路。
- 播放時熱區呈現要**看得出可點**（游標 `pointer` ＋高亮框有節奏的呼吸提示），並在字幕列標示「請點擊畫面上的指示位置繼續」；「下一步」按鈕在此步驟停用，但**「上一步」與側邊步驟清單跳轉不受限制**（給指揮官自己演練時退路）。
- 三個播放面**行為必須一致**：重播（設計工具內）、簡報模式（全螢幕）、以及 **UID13 離線匯出包**。匯出包是靜態 HTML，此邏輯需一併烘進 `renderFlowExportHtml`，不可只做線上兩處。
- **座標必須乘上 `presentScale`（2026-08-21 補正）**：畫面元素以 `el.x * presentScale` 排版（`renderReadOnlyElementsHtml`），熱區框原本用原生座標直出，於「裝置視角（device）」呈現 dp 畫面時會整個錯位（點不到）。`renderFlowAdvanceHotspotBox(step, presentScale)` 需一併換算。熱點編輯器固定 `presentScale:1`，所以存檔一律是原生座標，不受影響。
- **誠實邊界**：這裡的「點擊」是點在**熱區框**上，不是真的綁到畫面裡某個元件的事件；熱區位置由設計者自己拉框對準。此限制要在 UI 提示中講明，不得宣稱為真實互動。

### 7.4.8 播放載入的單一入口（2026-08-21 修正）

**症狀**：在編輯頁直接按「簡報模式」，全螢幕永遠停在「載入中…」；離開後連「重播」也跟著卡住。

**根因**：載入畫面的動作綁在 `startFlowReplay()` 裡，編輯頁的「簡報模式」按鈕自己造了一份 `flowPlay={loading:true}` 卻沒觸發載入，而 `enterFlowPresent()` 又因為「`flowPlay` 已存在」而略過補救 → 永遠沒人去抓畫面。殘留的 `flowPlay` 還會讓之後的重播面板一起卡在「載入中…」。

**修法（鐵則）**：播放狀態的載入收斂成唯一入口 `ensureFlowPlayLoaded()`——冪等（已載完或載入中都直接返回）、由重播與簡報模式共同呼叫。**日後再新增任何播放入口（例如從清單直接播、從演示分享連結播），一律呼叫它，不得各自 new 一份 `flowPlay`。**

### 7.4.9 頭像對話必須看得到 UI 設計系統的資料（2026-08-21 修正）

**症狀**：在「UI 設計系統」點頭像問「這條演示引用了哪些畫面」，Hana 憑印象把元件的預設文字（如「批量投入」「批量產出」）拼成不存在的畫面名稱。

**根因**：`views/uidesign.js` 有 `getChatContext()`（所以標題正確），但 **server 端沒有對應的 provider**，`payload` 也是空的 `{}` → 注入內容為零。`CHAT_CONTEXT_PROVIDERS` 對未知 kind 是「回空字串、不報錯」，所以這個缺口完全無聲。

**修法**：`payload` 帶當下的 id（`flowId` / `screenId` / `componentId` ＋ `mode`），server 端新增 `uidesign` provider 現讀 `<workspace>/.harness/uidesign/`，**先給本工作區真實存在的元件／畫面／範本／演示清單**（含 id），再給當下那一筆的細節；並明寫「清單裡沒有的就是不存在，不得臆造」。細節見 `SPEC-view-chat-context.md` §3.8。

**通則**：view 實作了 `getChatContext()` **只完成一半**，後端 provider 沒接等於 Hana 全瞎——而且症狀是「答得很順但內容是編的」，比報錯更難發現。新 view 上線自測要包含「在該畫面問一個只有讀得到資料才答得出來的問題」。

## 7.5 播放即真網頁：可互動原型（Charles 2026-08-21 拍板，UID16／UID17）

**指揮官原話**：「既然元件庫有了、畫布也有了，那輸出時不論是預覽或播放，應該就是直接用網頁的方式渲染，所以按鈕也要可以點，textbox 也要可以輸入、Radiobutton、下拉選單都可以選，CheckBox 可以勾……至於要什麼事件都是我們可以在該 UI 設計的時候來指定。」

這推翻了 D5 的「第一版只做畫面跳轉＋hover/按下的視覺回饋」——D5 之所以保守是怕滑向「做一個小型前端框架」，但實際上元件真身本來就是真 HTML 表單元素，**互動不需要新寫框架，只需要停止把它鎖住**。

### 7.5.1 根因分析（2026-08-21 實查）

唯讀渲染 `renderReadOnlyElementsHtml()`（`portal/views/uidesign.js`）與離線匯出 `buildStaticFrameHtml()`（`portal/uidesign.js`）都把**每個元件實例包成一個獨立的 `<iframe sandbox="allow-scripts" srcdoc>`，並一律加 `pointer-events:none`**。因此：

- 元件內容確實是真 HTML（不是圖片），但滑鼠事件在最外層就被攔掉 → 無 hover、游標不變、輸入框點不進去 → 觀感等同靜態圖片。
- UID15 的熱區是唯一 `pointer-events:auto` 的元素，所以「只有那一格能點」。

**重要修正（取代 2026-08-21 稍早的初步判斷）**：原本評估要「把整張畫面合併成單一文件」以取得連貫樣式，並列出元件 CSS 互撞的風險。實查後**不採用合併**——per-element iframe 的沙箱隔離正是「元件 CSS 永不互撞」的保證，合併反而製造風險。正確做法是**保留 iframe、解除 pointer-events 封鎖、並注入一支極小的事件橋接腳本**，成本更低且無樣式衝突風險。

### 7.5.2 D14 互動模型（拍板）

| # | 議題 | 決策 |
|---|---|---|
| D14 | 播放時如何取得真互動 | **保留每元件一個 sandbox iframe**（樣式隔離免費），移除唯讀渲染路徑上的 `pointer-events:none`，並在 `buildRenderSrcdoc()`／`buildElementSrcdoc()` 產生的 srcdoc 中注入 `UID_BRIDGE`：以 `postMessage` 把 `click`／`change`／`input` 事件（含元件實例 id、事件目標的選擇器與值、以及點擊在畫框座標系的位置）回報給父頁。**不加 `allow-same-origin`**（維持隔離）、**不加 `allow-forms`**（避免表單真的送出造成導航）。 |
| D15 | 第一版支援哪些「設計時指定的事件」 | **三種**：`navigate`（前往指定畫面）、`toast`（顯示一段提示訊息）、`toggle`（顯示／隱藏指定元件實例）。**跨頁資料流（把輸入值帶到下一頁）不在第一版**，列為 §7.5.5 後續。 |
| D16 | UID15 熱區怎麼辦 | **降級為純提示**：熱區框改 `pointer-events:none`（不再攔截點擊），改由橋接回報的點擊座標判定是否落在熱區內來決定前進。呼吸高亮與字幕提示照舊。既有流程資料與行為不變。 |

### 7.5.3 影響面（四個播放面必須一致）

| 面 | 位置 | 動作 |
|---|---|---|
| 全螢幕預覽（唯讀） | `renderReadOnlyElementsHtml` / `fillReadOnlyFrames` | 解除封鎖＋橋接 |
| UID3 可點擊原型播放 | 同上（共用唯讀渲染） | 同上；原有「點畫面任一處跳轉」的外層 wrap 監聽需與橋接點擊去重，避免一次點擊觸發兩次 |
| UID12 重播／簡報模式 | 同上 | 同上；熱區判定改走座標 |
| UID13 離線匯出包 | `buildStaticFrameHtml` / `renderFlowExportHtml` | 橋接腳本與事件表**烘死進靜態 HTML**，不得只做線上三處 |

**明確不動**：編輯畫布的元件 iframe（`portal/views/uidesign.js` 約 L1163）維持 `pointer-events:none`——那是拖曳與選取的前提，解除會讓畫布無法編輯。

### 7.5.4 誠實邊界

- **元件必須本身就是標準表單元素才會有互動**。元件庫是使用者自建內容，無法保證每顆都是；UID16 需產出一份**互動性盤點清單**（哪些元件含可互動元素、哪些純展示），據實回報，不得宣稱「全部都能互動」。
- **元件內若有跨出自身邊界的彈出層**（自訂下拉選單、tooltip），會被該元件的 iframe 邊界裁切。原生 `<select>` 的選單由作業系統繪製、不受影響。此限制須寫進盤點清單。
- **「按鈕會動」不等於「有商業邏輯」**：按下去發生什麼，一律以 UID17 設計時指定的事件為準；未指定就只有原生的視覺回饋。
