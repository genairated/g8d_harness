# SPEC-chat-concurrent-messages — 連續送訊息不鎖輸入框（背景處理＋關係判斷＋排隊／並行／合併）

> 狀態：草案 v0.1（2026-10-29 立案，Charles 口述需求；O1~O4 已於 2026-10-29 全依建議拍板，v0.2）

> 相關規格：`specs/SPEC-chat-background-task.md`（背景任務、回寫鎖、SSE）、`specs/SPEC-chat-durability.md`（送出即落檔）、`specs/SPEC-scheduler.md`

## 1. 問題

指揮官在 Hana 思考時，輸入框雖然還能打字，但**後端沒有「同時管理多件事」的機制**：新訊息只能等前一個做完，或由指揮官按停止鍵中斷。

指揮官真正要的是：

1. 每則訊息一送出就在背景獨立處理，**隨時能再送下一則**。
2. Hana 判斷兩則訊息的關係，決定怎麼處理（見 §3）。
3. 多則同時在跑時，**回覆要能對得上是哪一問**，且有關聯的可以合併成一則。

> 與 `SPEC-chat-background-task` 的差別：該規格是「Hana **判斷很久的事**才轉背景」；本規格是「**每一則**都走背景流程」。指揮官指出：事前根本無法預判會跑多久，所以不能靠臨場判斷。

## 2. 設計原則

- **不重造輪子**：沿用 `/api/chat` 既有的 job 登記（`jobs` Map、可列出／可中止／可重接）、`withChatSessionLock` 回寫鎖、SSE `chat-task-changed`。不另建新的執行引擎。
- **安全優先於速度**：不確定時一律「等前一個做完再接」，**寧可慢，不可丟掉做到一半的工作、不可兩件事同時改同一批檔案**。
- **對話是工作台、檔案才是記憶**：每則提問、每則回覆的對應關係必須落檔（`questionNo`、`replyTo`），重開對話仍對得上。

## 3. 兩則訊息的關係與處理方式

| 關係 | 判準（保守） | 處理 |
|---|---|---|
| **接續（補充）** | 後一則**明確是同一件事的補充或更正**（例如前一句需求沒講完） | 中止前一個，用「前文＋補充」合併成完整需求重做；回覆說明「已把你第 N 句併入第 M 句」 |
| **獨立** | 兩件不相干的事，且**至少一方明確是唯讀**（查資料、回答問題） | 並行，各自回覆，互不影響 |
| **有先後／可能改同一批檔案** | 後一件要用前一件的成果，或任一方可能寫檔 | **排隊**：前一個完成才接 |
| **不確定** | 以上都無法明確判定 | **排隊**（預設，不擅自中斷） |

規則：

1. **只有「明確是補充同一件事」才中斷**，其餘絕不中斷。
2. **寫檔工作一律排隊**（同一工作區內同時只有一個可能寫檔的工作在跑）；只有明確唯讀者可並行。
3. 指揮官**明確指示優先**：「這個先停」「這個同時做」「等上一個做完再做」→ 照辦，不用自己的判斷覆蓋。

## 4. 回覆方式（待決策 O2，建議如下）

- **預設各自回覆**，每則回覆開頭**引用原提問**（「回覆你的第 N 問：…」）。
- 介面上回覆**掛在對應提問下方**（第二階段，需改畫面）。
- 多則幾乎同時完成時，**依提問順序**排列，先完成的不插隊。
- **明確同一件事**才合併成一則，並註明「已把第 2 句併入第 1 句」。
- 不確定 → 各自回覆（不漏任何結果，風險最小）。
- 「彙整成同一則」的選項：兩個背景工作都完成後，多一次彙整處理，把結果寫成同一則回覆。**代價**：先完成者被拖慢、多花一次額度。僅在指揮官明說「合併回覆」時啟用。

## 5. 資料與機制（草案）

- 每則使用者訊息分配 `questionNo`（對話內遞增）；每則回覆帶 `replyTo: questionNo`、`meta.mode: 'queued' | 'parallel' | 'merged'`。
- 每條對話維護一個**佇列**：狀態 `queued / running / done / aborted`；與 `jobs` 對應。
- **關係判斷**（待決策 O1）：由一次輕量模型呼叫輸出 `{relation: 'continue'|'independent'|'dependent'|'unknown', readOnly: bool}`；**失敗或逾時一律視為 `unknown`＝排隊**。
- 回寫仍走 `withChatSessionLock` ＋ `saveChatSessionMerged`（附加，不整檔覆寫），沿用 `SPEC-chat-background-task` §3.2。
- **工作區隔離（鐵則）**：佇列、SSE、徽章都只在同工作區可見，比對前 `path.resolve()`＋小寫正規化。

## 6. 分階段

| 階段 | 內容 | 不含 |
|---|---|---|
| **P1 後端** | 每則訊息登記為 job、佇列（排隊／並行）、關係判斷（失敗＝排隊）、`questionNo`／`replyTo` 落檔、回覆開頭引用原提問、中斷＋合併重做（僅明確補充） | 畫面改動 |
| **P2 前端** | 回覆掛在對應提問下、佇列狀態小卡（排隊中／執行中／已併入）、單筆中止、徽章 | 彙整合併 |
| **P3 彙整** | 指揮官明說「合併回覆」時的彙整步驟 | — |

## 7. 風險（誠實揭露）

1. **誤判**：把「獨立」誤看成「接續」而中斷，會丟掉做到一半的工作。對策：中斷門檻極高，疑慮一律排隊。
2. **同時改同一批檔案互相覆蓋**：對策：寫檔工作一律排隊（§3 規則 2）。
3. **額度**：並行會更快用掉額度，撞限額機率提高；既有「限額自醒續跑」會接手。
4. **判斷本身耗額度與時間**：每則多一次輕量呼叫；對策：失敗即排隊，不阻塞。
5. **回寫競態**：多個背景工作同時完成回寫，鎖沒做對會吃掉訊息，需針對性測試（沿用 CBG 經驗）。

## 9. 驗收條件（AC，草案）

1. 連送兩則獨立的唯讀問題 → 兩則同時處理，各自回覆，每則開頭標明對應第幾問。
2. 連送兩則可能寫檔的工作 → 第二則顯示「排隊中」，第一則完成後自動接續。
3. 第二則明確是第一則的補充 → 第一則被中止、以合併後需求重做，回覆註明已併入。
4. 無法判定關係 → 一律排隊，不中斷任何工作。
5. 兩則幾乎同時完成 → 依提問順序顯示，沒有任何一則消失。
6. 重開對話 → 每則回覆仍對得上原提問。
7. 工作區 A 的佇列在工作區 B 完全看不到。

## 11. P1 實作備註（2026-10-30，尚未部署）

**程式位置**：純邏輯 `portal/chat-queue.js`（佇列、指示解析、判斷結果解析、回覆標示、依序落位）；接線在 `portal/server.js`（`chatQueue`／`cmqSubmit`／`cmqRelease`／`respondChat` 的 CMQ 段／`GET /api/chat/queue`）。

**行為**
- `POST /api/chat` 不再直接開跑，一律 `cmqSubmit`。對話裡沒有其他活著的訊息 → 立刻開跑（`mode=solo`，不呼叫模型、不加標示，單則對話與現況一致）。
- 有其他活著的 → 先看指揮官明確指示（先停／同時做／等上一個），否則呼叫輕量模型（`haiku`，沿用 `_tgSpawnClaude`，25 秒上限）判斷。**失敗、逾時、格式錯誤、`unknown`、`dependent` 一律排隊。**
- 並行條件：`independent` 且新舊兩則都明確唯讀。其餘排隊（FIFO，同對話同時只有一個非並行者在跑）。
- 明確補充（`continue`，且兩則都不是斜線指令）：前一個執行中 → 標記被取代並中止，**等它真正結束後**合併者才開跑（避免兩個同時改檔），其回覆靜默不落檔；前一個還在排隊 → 直接取消，合併者接位。合併者的 prompt 在開跑時才以「前文＋補充」＋當下硬碟上的對話重建，所以排隊者看得到前一個的成果。
- `questionNo` = 該則使用者訊息在對話內的序數，蓋在使用者訊息上落檔；回覆帶 `replyTo`（頂層）與 `meta.mode`（`queued`/`parallel`/`merged`）、`meta.mergedFrom`。多則在跑時回覆開頭加「回覆你的第 N 問：…」。
- 回寫沿用 `withChatSessionLock`＋`saveChatSessionMerged`（新增選用參數 `insertFn` 做依提問順序落位；不帶則完全是舊行為）。同對話還有別的訊息在跑時，保留 `pending` 標記不被清掉。
- 工作區隔離：佇列鍵為「正規化工作區＋sessionId」；SSE 沿用 `broadcastChatTaskChange`（本來就依工作區過濾），新事件 `chat-queue-queued/started/finished`；`GET /api/chat/queue` 只回當前工作區（`X-Workspace`）。
- 排隊中的 job `status='queued'`：算「未完成工作」（延後重啟會等它）、可用既有 `/api/jobs/:id/abort` 取消。

**我採用的預設（O1~O4 已拍板，以下是實作細節上的選擇，請指揮官確認）**
1. 「寫檔工作同一工作區只跑一個」只在**同一條對話內**強制；不同分頁（不同對話）之間維持現況各自並行，沒有加工作區層級的全域鎖——否則會破壞既有「多分頁並行」。
2. 單則對話（沒有第二則在跑）回覆不加「回覆你的第 N 問」標示，避免每則都多一行引用。
3. 輕量模型用 `haiku`；用量記帳目前沿用 Telegram 輕量呼叫的標籤（trigger=telegram），帳上歸類會不準。

**已知限制／未驗證**
- 尚未用真 CLI 做端到端；輕量模型判斷的實際準確度未測。
- 前端（P2 才改）收到「被併入／排隊取消」的請求回應（`superseded:true`／`cancelled:true`，reply 為一句說明、不落檔）時的顯示未驗證。
- 並行的兩個工作共用同一份 `context_<sessionId>.md`，後寫者覆蓋；只影響 prompt 內的歷史片段，不影響落檔。
- 排隊中的訊息若遇 server 重啟會遺失執行（使用者訊息已落檔，但需重送）。
