## 1. 動機與一句話定義

指揮官要能回答兩個問題：**「我的額度被誰吃掉了？」** 與 **「這支技能／這條排程是不是變肥了？」**
`SPEC-model-quota` 只顯示帳號層級的剩餘百分比，無法歸因到「某一次執行」。本規格補上**逐次執行的 token 帳單記錄**，再在其上做**統計視覺化**。

**用途明確**：資料的第一用途是「優化技能與提示詞」，第二用途是「挑時間、避開限額」。不是成本會計，不需要精確到分錢。

## 2. 設計決策（已與指揮官拍板，實作紅線）

| # | 決策 | 理由 |
|---|---|---|
| D1 | **不用「額度百分比前後相減」反推單次用量** | 官方只給整數百分比窗口，且多任務並行（排程＋對話同時跑）會把別人的用量算到這筆頭上。誤差無規律，會誤導技能優化 |
| D2 | **直接向 CLI 索取帳單**：Claude Code 改用 `--output-format json`，讀回傳的 `usage`（input / output / cache_read / cache_creation）與 `total_cost_usd` | 精確值、不額外花額度 |
| D3 | **覆蓋率不完整要誠實標示**，不得估算填空：Claude＝精確；Codex＝近似（本機紀錄）；Antigravity/Gemini＝官方不給 → `source:"unavailable"` 留空 | 誠實原則（沿用 `SPEC-model-quota` D3）。假數字比沒數字危險 |
| D4 | 分類用**兩個互相獨立的欄位**，不是一個混合分類：`trigger`（來源）與 `skill`（做什麼事） | 一個分類欄位沒辦法同時回答「排程吃掉多少」與「哪支技能最肥」 |
| D5 | **對話內背景任務（§CBG/§CBGV）歸入 `trigger:"chat"`**，另以 `background:true` 標旗 | 指揮官拍板：它是對話的延伸，不是他排的定時任務。旗標保留日後拆開看的能力 |
| D6 | ~~**X-Bar/R 管制圖不用於「對話的每一輪」**~~ **（2026-10-03 指揮官推翻，改為實作，見 D11）** | 原理由：X-Bar/R 要求組內是隨機變異。但指揮官指出他要的分組是「一天的一個對話＝一組」，X̄ 答「這個對話平均一輪多少」、R 答「這個對話從頭漲到尾差多少」——後者正是「該不該關掉這個對話」的判斷依據。見 D11 |
| D7 | ~~**X/MR 管制圖只開給「同一件事的重複執行」**：挑單一排程／單一技能~~ **（2026-10-03 修訂，見 D12）** | 原則仍對，但實作把「挑哪一支排程」當成下拉維度是錯的：單一排程常只有 1~2 個點、永遠畫不出圖，且下拉顯示內部代號（`排程：521_m6xc`）指揮官看不懂。改為**按類型過濾**（見 D12） |
| D8 | 管制線計算**先取對數**（或改用中位數／IQR），不直接對原始值算 ±3σ | token 用量高度右偏，直接算會把正常值判成異常 |
| D9 | 新增一個獨立的**統計頁面掛進側欄 menu**，不塞進既有排程頁 | 它同時涵蓋對話與排程，不屬於任何單一既有頁面 |
| D10 | **menu 項目一律用 lucide icon，標籤文字不得含 emoji** | 已有護欄 `portal/checks/menu-no-emoji.js`，Deploy 會擋。本頁新增 menu 時一併遵守 |
| D11 | **實作 X-Bar/R，分組＝「同一天的同一個對話」**（一組＝該日該 session 的所有輪次） | 指揮官拍板。X̄＝該對話平均每輪用量，R＝該對話頭尾落差。R 大＝這個對話越聊越貴、該收掉開新的。**誠實標註**：此處 R 的語意是「漲幅」而非教科書的隨機變異，圖上必須寫明，不得當成標準品管警報使用 |
| D12 | **X/MR 的下拉改為「類型過濾」而非「挑某一支」**：全部／僅對話／僅排程／某支技能 | 挑單一排程常只有 1 個樣本點，永遠畫不出圖。且下拉不得顯示內部 ID，要顯示人看得懂的名稱；樣本數不足（<8）的選項直接不列入下拉，不要讓指揮官選了才發現空白 |
| D13 | **Pareto 必須有「按對話」這一組**，與按技能／按排程並列，且**預設就是按對話** | 指揮官最常做的是一般對話，原版只有技能／排程兩種分組，等於漏掉主力用量。他要的決策是「這個對話還能不能繼續聊，還是該關掉」 |
| D14 | **所有圖表的軸標籤／下拉選項一律顯示人看得懂的名稱**，不得出現截斷的內部 ID | 排程→排程名稱、技能→技能名、對話→對話標題（取不到標題才退回日期＋短代號，且要標示「未命名對話」）。這是 D3 誠實原則的延伸：看不懂的標籤等於沒有資訊 |
| D15 | **Pareto 移除「按排程」分組**，只留「按對話」（預設）／「按技能」 | 排程只跑一次，放進排行榜沒有意義；指揮官看柏拉圖的目的是判斷「對話該不該保留或壓縮」 |
| D16 | **G3 分佈箱型圖整張移除**，不保留「沒資料自動隱藏」的過渡做法 | 目前多數工作區都沒叫技能，留著長期是空的；之後若技能用量變多，要加再加，不先佔位 |
| D17 | **G4（X/MR 個別值管制圖）整張移除，改為新圖「使用量趨勢（X-Bar/R，固定組距）」**：依事件時間序，每 N 筆事件打包成一組（N＝下方 D19「組大小」），一組一個點，畫 X̄（組平均）與 R（組全距）；疊兩條參考線——①管制界限（取最近 W 組算 CL/UCL/LCL，W＝D19「管制界限視窗」，算法沿用既有 D8 對數法）②歷史百分位（取最近 P 組，P＝D19「歷史百分位視窗」，算「這組比過去 P 組中幾 % 都高」），兩條並列、不互斥 | 指揮官實測後認為 X/MR 看不出意義；某客戶專案的模擬器用固定樣本數分組的 X-Bar/R 才是他想看的「用量趨勢、超出管制界限的軌跡」。歷史百分位解決「管制界限假設常態分布」在非重複性對話場景不成立的問題（誠實標記、非教科書警報） |
| D18 | **既有 G5（分組＝「同一天的同一個對話」，回答「該不該關掉這個對話」）維持不動**，與 D17 新圖並存、不互相取代 | 兩張圖回答不同問題：D17 看「整體用量趨勢有沒有失控」、G5 看「這一個對話還能不能聊下去」，分組依據本質不同（固定筆數 vs. 對話生命週期），不應合併成一張。**本條為本次（v0.6）綜合指揮官原話後的設計判斷，非逐字拍板**，若指揮官看到新圖後認為 G5 已多餘，之後可再拿掉 |
| D19 | **新增「設定統計指標」彈窗**，可調三個參數：**組大小**（每幾筆事件打包成一組，預設 ~~5~~ **3，v0.7.1 起，見 D32**）、**管制界限視窗**（管制線取最近幾組計算，預設 25——業界 SPC 常見的基線組數）、**歷史百分位視窗**（取最近幾組算百分位，預設 100，可設「全部」）。改完按**「儲存並重算」**才套用並關閉彈窗，取消不套用 | 指揮官要自己調靈敏度／近期感，不要我幫他固定一個數字；三個數字互相牽動（抓太多失去近期感、抓太少樣本不足），讓他自己試 |
| D20 | 三個參數**存檔於工作區**，路徑 `.harness/runtime/usage/settings.json`，依既有工作區隔離慣例過濾 | 設定要跨瀏覽器分頁/重新整理後還記得；跟其他用量資料用同一套隔離規則，不另開一套 |
| D21 | **G4 的管制界限改用教科書 X-Bar/R 公式**：`CL = X̄̄`（視窗內各組的加權總平均）、`UCL/LCL = X̄̄ ± A2·R̄`，R 子圖補 `R̄`／`UCL_R = D4·R̄`／`LCL_R = D3·R̄`；**D17 原文「算法沿用既有 D8 對數法」就此作廢** | 指揮官實測指出兩個症狀：①中心線沒落在上下界限中間 ②每一個點都在界限內、圖沒有任何警報能力。根因是 D8 的對數 ±3σ 法——CL 是幾何平均，在線性 Y 軸上不可能居中，且 ±3σ 在對數空間等於乘法級的寬度。既然這張圖叫 X-Bar/R，就該用 X-Bar/R 的公式（與 G5／D11 同一套 Montgomery 常數表），不另創算法 |

## 3. 資料契約

### 3.1 一筆用量記錄（usage event）

```jsonc
{
  "id": "ua_1790901667910_ab12",
  "at": "2026-10-02T06:12:33.000Z",   // 執行結束時間（UTC ISO）
  "workspace": "D:\SideProject\g8d_harness",
  "trigger": "chat",                   // chat | schedule | telegram   ← D4/D5
  "background": false,                 // true = 對話內背景任務（trigger 仍為 chat）
  "skill": "task",                     // 技能名（無技能的一般對話＝ null）
  "sessionId": "session_...",          // trigger=chat 時有
  "scheduleId": "sched_...",           // trigger=schedule 時有；對話衍生的一次性任務也帶
  "provider": "claude",                // claude | codex | agy
  "model": "opus",
  "tokens": {
    "input": 12043,
    "output": 2310,
    "cacheRead": 98211,
    "cacheCreate": 0,
    "total": 112564
  },
  "costUsd": 0.1842,                   // CLI 給就記，給不出就 null
  "elapsedMs": 41231,
  "source": "claude --output-format json"   // 或 "codex-approx" / "unavailable"
}
```

**缺資料的表示法（D3）**：`tokens` 全為 `null`＋`source:"unavailable"`。**不得補 0**——0 會被統計當成「這次沒花錢」，比留空更錯。

### 3.2 儲存位置

`.harness/runtime/usage/YYYY-MM.jsonl`（每月一檔，append-only）。
**理由**：沿用既有 runtime 目錄慣例、按月切檔避免單檔無限長、JSONL 可直接 append 不必整檔讀寫。
**工作區隔離**：每筆帶 `workspace`，讀取面一律照 `SPEC-scheduler` 既有 pattern 過濾（`path.resolve()`＋小寫正規化，`null`＝`WORKSPACE_ROOT`）。

### 3.3 查詢 API

- `GET /api/usage/events?from=&to=&trigger=&skill=&provider=` → 原始事件（上限 2000 筆，超過回 `truncated:true`，**不得靜默截斷**）
- `GET /api/usage/summary?from=&to=&groupBy=skill|trigger|provider|model|day` → 預彙總
- `GET /api/usage/control-chart?subject=skill:task|schedule:sched_xxx` → ~~X/MR~~ **（v0.6 移除，見 D17；端點保留但前端不再呼叫，避免破壞尚未更新的快取頁面）**
- `GET /api/usage/trend` → **（v0.6 新增，D17）** 取代上一行。依工作區當前設定（D19）的組大小／管制界限視窗／歷史百分位視窗，回傳固定組距的 X̄/R 點序列＋管制界限＋歷史百分位線；組數不足（< 管制界限視窗門檻）明確回 `insufficientData:true`
- `GET /api/usage/xbar-r` → 既有端點**不動**（D18），仍是「同一天同一對話」分組
- `GET /api/usage/settings` → **（v0.6 新增，D19/D20）** 讀目前工作區設定；檔案不存在回系統預設值（組大小 ~~5~~ **3，v0.7.1，D32**／管制界限視窗 25／歷史百分位視窗 100），不落檔
- `PUT /api/usage/settings` → **（v0.6 新增）** 寫入並回傳儲存後的值；驗證：組大小整數 2~50、管制界限視窗整數 ≥8、歷史百分位視窗整數 ≥10 或字串 `"all"`；驗證失敗回 400、不寫檔
- **（v0.8 新增，D34）所有 `GET /api/usage/*` 查詢端點一律接受 `scope=current|all`**（預設 `current`＝只讀當前工作區，行為與 v0.7.2 完全相同）。`scope=all` 時後端依 `global-knowledge/projects.json` 去重展開工作區清單（含當前工作區，見 D36），逐一讀各自的用量目錄合併後才套用篩選／分組，回傳的每筆事件與每個分組都帶 `project`（專案顯示名）。`PUT /api/usage/settings` **不接受 `scope`**（設定永遠寫當前工作區）

### 3.4 設定檔格式（D19/D20）

```jsonc
// .harness/runtime/usage/settings.json
{
  "groupSize": 3,         // 組大小：每幾筆事件打包成一組（系統預設，v0.7.1 起，D32；此檔存在時一律以檔案值為準）
  "controlWindow": 25,    // 管制界限視窗：取最近幾組算 CL/UCL/LCL
  "percentileWindow": 100, // 歷史百分位視窗：取最近幾組算百分位；"all" = 不限
  "updatedAt": "2026-10-08T00:00:00.000Z"
}
```
純資料檔，改這個檔不需要 Deploy；但讀寫它的程式碼（`usage-tracker.js`／`server.js`／`usage.js`）仍要走 Deploy 才會生效。

## 6. 風險與已知限制（誠實記載）

1. **最大風險**：Claude Code 由 `--print`（純文字）改 `--output-format json` 會改變程式讀回覆的方式，解析寫錯＝**回覆變空白**。這是會被立刻看見的壞法，不是隱性錯誤。必走 `Deploy_Harness.ps1`（冒煙測＋失敗回滾）。
2. **歷史資料沒有數字**：上線前的對話與排程當時沒記，統計只能從上線日起算。不得回填猜測值。
3. **覆蓋率不均**：Codex 近似、Gemini 無資料（D3）。統計頁必須把「無資料筆數」顯示出來，不可讓指揮官誤以為看到全貌。
4. **效能**：事件數成長後 `summary` 若每次重算全月會慢 → 先做每日預彙總快取。
5. **「佔週限額」是推估值，不是帳單**（v0.7 D29）：官方用量端點只回傳「當下」的 5 小時／7 天窗口使用率，**沒有歷史週的百分比**，所以歷史週只能用「當下使用率回推的週限額」換算。兩個已知偏差：①本頁只記得到**本工作區**的用量，帳號層級的實際使用率一定更高（別的工作區、直接開 CLI 用掉的都不在內）→ 這裡的百分比**偏低**；②回推的分母跟著當下快照走，不同時間打開看到的歷史週百分比會有差異。畫面上已標註，但不得把這個數字當成「還剩多少可以用」的唯一依據。
6. **管制界限的基數不足**（v0.7 D28）：8 ≤ 組數 < 管制界限視窗時照畫，但界限只用手上那幾組算，容易偏窄→誤報出界。畫面已標註「當初步訊號看」；真正要判讀 OOC 應拉長區間讓組數接近設定的視窗。
7. **G5 的固定界限不是教科書做法**（v0.7 D27）：各組對話輪數不等時，標準 X-Bar/R 應該用變動界限。本圖為了「一眼看出哪個點出界」刻意用平均輪數算成固定界限，屬設計取捨，已在圖上標註，不得對外當成標準品管圖引用。
